## 2. Critical blockers

### C01 — BLOCKED: H2 Payment ID ownership has no all-writer database guarantee

The database enforces only `(user_provider_account_id, provider_payment_id)` on `nium_virtual_accounts`. Different local account rows may therefore hold the same literal Payment ID. Operations have a nonunique account/payment index and a separate unique account/operation key, not a Payment ID ownership constraint ([VA migration:22](/home/dtd1201/projects/api_origin_wallet/database/migrations/2026_08_06_000001_add_nium_payment_safety_fields.php:22), [operations migration:31](/home/dtd1201/projects/api_origin_wallet/database/migrations/2026_10_20_000001_create_nium_virtual_account_operations_table.php:31)). No frozen origin/client/customer/wallet ownership columns exist on historical VA rows in those definitions.

Participating ledger resolvers take a literal-ID PostgreSQL advisory transaction lock and check all VA/operation rows; the helper explicitly requires READ COMMITTED and explicitly excludes historical/raw writers from its guarantee ([SafetyLedger.php:233](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:233), [SafetyLedger.php:384](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:384)). The current legacy webhook also uses that helper ([NiumWebhookService.php:581](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumWebhookService.php:581)). **Legacy reconciliation does not**: its public `assign()` locks the operation, searches within one local account, and updates/inserts a VA without the account/scope/ID locking protocol ([ReconciliationService.php:145](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountReconciliationService.php:145)). VA and detail models expose mutable ownership fields with no model-level immutability hook ([NiumVirtualAccount.php:15](/home/dtd1201/projects/api_origin_wallet/app/Models/NiumVirtualAccount.php:15), [NiumVirtualAccountDetail.php:11](/home/dtd1201/projects/api_origin_wallet/app/Models/NiumVirtualAccountDetail.php:11)). The enrolled operation trigger protects its link, not subsequent mutation of the linked VA itself ([single-dispatch migration:40](/home/dtd1201/projects/api_origin_wallet/database/migrations/2026_10_27_000002_support_nium_va_single_dispatch.php:40)).

Concrete permitted race: a ledger resolver checks an ID under its advisory lock while a legacy resolver for another local account writes the same ID without that lock. Both account-scoped unique constraints can succeed. A later check may quarantine the collision, but cannot retroactively establish which account is the provider-authoritative owner. This is a source-derived possibility, not a reproduced incident.

**UNKNOWN:** NIUM's identifier domain, historical duplicate/alias inventory, actual database constraints/roles, external maintenance writers, and authoritative ownership for existing rows. Missing evidence: written NIUM domain rules plus an authorized read-only historical inventory and database/schema/process attestations. Do not infer global uniqueness or install a guessed global unique index.

Smallest safe options, proposed only:

- **Preferred scoped ownership registry:** after NIUM confirms the domain, retain immutable domain components and an ownership claim keyed by `(confirmed_domain, exact_payment_id)`. Enforce claim/VA/operation agreement transactionally and at the database boundary; all writers must use the same claim protocol or be denied. An equivalent constraint on VA rows is smaller only if it also covers operation-only claims and link/owner mutation safely.
- **Conservative interim hold:** prohibit all new allocations/attachments outside a completely fenced cohort, quarantine duplicate literals, and preserve unresolved scopes until historical ownership is adjudicated. This reduces exposure but does **not** close H2 for general Production use.
- A global literal-ID unique index is acceptable only with explicit NIUM confirmation of that domain and a clean, reviewed inventory. Adding the advisory helper to one more service alone is insufficient because raw/model writers still bypass it.

### C02 — BLOCKED: legacy/new collision and rollback remain possible

Routing is conditional, not a global fence. Enrolled keys always route to the new service; enabled + new key routes there too. Existing legacy keys can still resume legacy reconciliation. Disabled + new key can enter legacy claim/GET/POST unless the current account or current wallet string already has an enrolled history. This history check occurs before the legacy account lock and is not rechecked inside `claim()` ([NiumPaymentIdService.php:62](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumPaymentIdService.php:62), [NiumPaymentIdService.php:189](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumPaymentIdService.php:189)).

The new service's allowlist and `old_workers_fenced` boolean are checked only for new enrollment. The boolean does not inspect or stop an old process; the gate is not repeated at the final authorization or sole POST site ([AssignmentService.php:38](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountAssignmentService.php:38), [AssignmentService.php:95](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountAssignmentService.php:95), [SafetyLedger.php:96](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:96)). Disabling a feature cannot recall an authorization already committed or a request already in flight.

Other collision surfaces:

- Public legacy `assign()` refuses an enrolled **operation**, but does not prohibit resolving another legacy operation on an enrolled wallet. It can create/attach a VA and can change a legacy operation's existing link if called directly with a different ID ([ReconciliationService.php:145](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountReconciliationService.php:145)).
- Current legacy webhooks check enrollment under the account lock; the earlier alias/customer/wallet screening reduces fallback risk. An older binary or unknown historical alias does not inherit that protection ([NiumWebhookService.php:495](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumWebhookService.php:495), [NiumWebhookService.php:586](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumWebhookService.php:586)).
- A CLI invocation without `--operation-id` generates a fresh key; rerunning the command is a new allocation intent ([AssignNiumPaymentId.php:13](/home/dtd1201/projects/api_origin_wallet/app/Console/Commands/AssignNiumPaymentId.php:13)). Different keys are not deduplicated by account/currency forever: terminal resolution releases the scope ([SafetyLedger.php:246](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:246)).
- The legacy barrier inspects operations, accepting `assigned` + timestamp + syntactically valid ID as conclusive; it neither verifies original provider proof nor inventories orphan VA rows ([SafetyLedger.php:337](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:337), [OperationState.php:34](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountOperationState.php:34)).

**UNKNOWN:** live old binaries, queues/reservations, cron/operator scripts, in-flight POSTs, aliases, and NIUM automatic allocation settings. Missing evidence: complete process and intent inventory, fence/drain attestations, and provider allocation confirmation. See section 7 for the proposed safe cutover and rollback.

## 3. High-priority blockers

### H01 — BLOCKED: delayed assignment, failure, and enum recovery contract is incomplete

Only direct persisted, correlated POST HTTP 200 success with a real `uniquePaymentId` can currently establish enrolled assignment. `INITIALIZED` yields pending; 202, malformed responses, transport/persistence failures and nonmatching responses remain unknown. GET discovery does not establish creation causality, and a webhook can resolve only when it agrees with the already-correlated successful POST ([AssignmentService.php:60](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountAssignmentService.php:60), [AssignmentResponse.php:54](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountAssignmentResponse.php:54), [ReconciliationService.php:209](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountReconciliationService.php:209), [NiumWebhookService.php:534](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumWebhookService.php:534)). Thus an initial POST returning only INITIALIZED cannot become assigned through a standalone later webhook/listing, even if NIUM allocated successfully. Losing the success response before durable capture has the same gap.

The webhook contract rejects any supplied `accountType`, `accountCategory`, `bankName`, or `fullBankName`: their equivalence to POST rails/codes is unverified. A same-target, same-ID receipt with such fields can also veto a later direct POST resolution. Failure notifications are retained as uncorrelated observations and cannot release a scope ([WebhookContract.php:115](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountWebhookContract.php:115), [WebhookContract.php:132](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountWebhookContract.php:132), [NiumWebhookService.php:521](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumWebhookService.php:521)). This fails closed, but is not a complete Production lifecycle.

Even V2's narrow HTTP 400 rejection primitive is not used by the normal orchestrator/reconciliation flow: the primitive supports specified validation errors, while the orchestrator transitions nonsuccess to unknown and reconciliation skips non-200 logs ([SafetyLedger.php:216](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:216), [SafetyLedger.php:405](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:405), [ReconciliationService.php:295](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountReconciliationService.php:295)). There is no V1 rejection rule or manual authoritative terminal resolution path.

**UNKNOWN:** actual delayed-success frequency/schema, provider causal recovery identifiers, enum/bank mapping, failure definitiveness and permitted support proof. Missing evidence: written NIUM contracts and representative redacted provider evidence. Required outcome: a reviewed asynchronous resolver/support procedure that never repeats POST or clears uncertainty by timeout.

Required setup is listed in section 8. **UNKNOWN:** installed consumers, scheduler, alert rules, dashboards, on-call owner and recovery SLA; missing deployment and operational evidence.

## 7. Legacy cutover risks

**BLOCKED C02:** old processes can still create/attach/modify legacy VAs after a future enrolled activation unless actually fenced. Current enrolled guards reduce overlap but cannot alter an older executable, deny arbitrary DB DML, or stop an authorized POST already in flight. Current service does not globally pause legacy allocation; legacy reconciliation remains a writer (W02/W03/W05/W07/W11).

Proposed cutover, for later implementation/authorization only:

1. Obtain NIUM domain/allocation/recovery confirmation and review the complete deployable candidate. Keep new allocations paused while investigating historical data. Preserve all caller keys, targets, exchanges, receipts and attempts.
2. Enumerate every API/CLI/worker/cron/manual/provider-automatic writer and all queues, reserved deliveries and in-flight requests. Prevent new legacy starts, drain or stop old processes, and prevent restart/retry from deploying the old binary. Disable/restrict unused provider credentials and database write paths through a reviewed operator plan, without breaking authenticated receipt capture or read-only recovery.
3. Wait for a documented drain boundary; any request whose outcome or drain completion cannot be established is **uncertain**, not “not sent.” Reconcile only through authoritative proof; quarantine its wallet/domain/currency. Legacy failed, claimed, preflight_failed and orphan records need review, not automatic new keys. Source barrier treats generic legacy failed as unresolved ([OperationState.php:34](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountOperationState.php:34)).
4. Inventory historic IDs/aliases/owners and resolve conflicts before installing the confirmed-domain ownership enforcement. Do not automatically enroll old operations; `prepare()` rejects that transformation ([ledger:40](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:40)). Preserve records whose origin/client cannot be established in quarantine.
5. Rehearse additive migrations under a controlled write/lock window, then attest installed triggers/constraints and process fencing. Deploy all readers and writers together with new allocations still paused. Configure the dedicated database consumer, session affinity, recovery scheduling, quotas and alerts.
6. Establish separate controls for **new allocation pause**, **read-only reconciliation/enrichment**, and **authenticated webhook receipt/recovery**. Freeze the approved V1 corridor and allowlist; a flag must not cause silent legacy fallback. Require an actual final dispatch decision compatible with pause semantics; already-consumed authorizations need explicit in-flight accounting.
7. After technical-lead/provider/operations acceptance, enable a bounded cohort under separate approval. Monitor one canonical operation and one dispatch token per intent; permit another same-currency VA only as a distinct intentional request after definitive prior resolution. Do not make wallet/currency permanently unique: multiple deliberate VAs are supported by scope release ([ledger:266](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumVirtualAccountSafetyLedger.php:266)).

Rollback/pause strategy:

- Stop **new allocation admission** and fence dispatchers; preserve history and read-only recovery. A consumed authorization can still be in flight, so do not mark it unsent or mint a replacement key based on a pause.
- Keep the fence across all accounts in the cutover population, including not-yet-enrolled accounts. Simply setting `enabled=false` restores legacy routing for some such accounts and is not a safe rollback ([service:62](/home/dtd1201/projects/api_origin_wallet/app/Services/Nium/NiumPaymentIdService.php:62)).
- Never delete/restore a pre-assignment database snapshot to reauthorize a provider POST; never delete attempts, rekey unknown intents, clear active scopes on timeout, or run destructive migration down paths. Use forward-compatible code that understands the existing ledger and evidence.
- Continue capturing immutable authenticated receipts during investigation. Retry GET/receipt processing under the existing proof rules; use provider/support evidence only through a separately reviewed authoritative procedure. If that procedure does not exist, leave allocation paused/unresolved.

These are design prerequisites, not commands executed or permission to activate.
