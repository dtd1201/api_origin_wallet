Release decision: **NO-GO for real execution**. The financial admission block remains intact. Expected fee zero is an internal business expectation. The available client Fee Details v2 contract does not establish effective customer pricing, complete source-wallet charge allocation, or an enforceable charge ceiling covered by the principal reservation. Post-dispatch debit evidence cannot supply that pre-dispatch funding safeguard. No live NIUM request, Remittance POST, Production change, commit, push or deployment was performed.

## Pricing adapter acceptance (2026-10-30)

The adapter now inspects existing encrypted Customer Details and Fee Details captures. It verifies capture version, GET/HTTP 200, response bytes/hash/length, request UUID/header hash, configured NIUM origin, provider and client. Customer selection additionally requires the owning user and exact customer identity, with client/wallet identity checked whenever returned. A unique active plan matching an explicit customer segment establishes a segment match only. A null segment never establishes DEFAULT assignment. Missing, stale, changed or ambiguous captures remain unavailable; reading pricing never requests a provider refresh.

FX rule inspection uses exact decimals, active status, currency matching, amount slabs and pair specificity over ANY/ANY. Equally specific overlapping rules are rejected. Slab comparisons using the source principal are explicitly diagnostic until NIUM confirms the legacy payout's slab amount/currency basis. Matching configuration cannot authorize dispatch. No payout fee or separate wallet debit is calculated from FX markup, and absent REMIT_BANK_FEE rows remain unknown.

Saved NIUM OpenAPI version `2026.10.28` defines `GET /api/v2/client/{clientHashId}/fees` (`getClientFeeDetailsV2`), requiring path `clientHashId`, header `x-request-id` and inherited API-key authentication. Its response is an array of `#/components/schemas/ClientFeeDetailsResponseDTO`, with fee rows in `#/components/schemas/FeeResponseDTO`. The response lists client plans; it does not identify a particular customer's effective assignment. `#/components/schemas/CustomerDetailResponse` describes `segment` as the applicable fee segment or null, without an explicit null-to-DEFAULT guarantee. `FeeResponseDTO.fixed=false` identifies a percentage; the saved V2 field description does not explicitly define the numerical scaling of the reported `0.13`, slab currency/boundary rules or threshold interaction. The percentage-points example on legacy `additionalFxMarkup` is a different field and is not used as proof of these V2 semantics.

`#/components/schemas/FxHoldLockResponseContent.fx_rate` is explicitly the effective rate after deducting `markup_rate`. The existing legacy locked rate is used unchanged; the adapter never adds or subtracts the configured markup again. This establishes FX rate treatment, not complete payout charges or the final wallet debit.

The reported Production observations (customer segment null; one active DEFAULT plan; USD/SGD FX_MARKUP 0.13; no REMIT_BANK_FEE row) and the user's negotiated-pricing confirmation do not establish complete charge allocation or a funded ceiling. The isolated worktree has no Production database or encrypted captures. Read-only inspection of the existing local database found no matching Customer Details/Fee Details logs and no encrypted exchange-evidence table. Consequently, the reported Production response hashes, environment and client/customer bindings could not be independently verified. Synthetic tests do not replace those captures.

Confirm V2 percentage/slab/threshold semantics if configuration is to be used for admission. The existing principal-only safeguard remains blocked. ## Available provider capability

The existing saved NIUM OpenAPI contract for `GET /api/v1/client/{clientHashId}/customer/{customerHashId}/wallet/{walletHashId}/transactions` exposes paginated wallet activity, `authCode`, client/customer/wallet IDs, debit direction, authorization currency and amount, settlement status and `settlementAuthAmount`. NIUM's Transactions guide identifies `Remittance_Debit`, `Remittance_Debit_External` and separate `Fee_Debit` records as wallet-impacting transactions. The Transaction Response Labels guide documents `originalAuthorizationCode`, which binds a fee to its original transaction. These contracts were already saved in the workspace; implementation made no network requests and adds no provider endpoints or manual evidence bundles.

References: [Transactions API](https://docs.nium.com/api#tag/customer-wallet-transactions/GET/api/v1/client/{clientHashId}/customer/{customerHashId}/wallet/{walletHashId}/transactions), [transaction types](https://docs.nium.com/docs/transactions), [response labels](https://docs.nium.com/docs/transactions/response-labels).

`NiumPayoutDebitReconciliation` reuses the authenticated NIUM transport and encrypted exchange capture. A status reconciliation explicitly reads wallet activity outside database transactions, without redirects, retries or payment/FX requests. The bounded full-wallet scan includes separate fee rows rather than assuming a remittance filter includes them. All pages and counts must be available; scans exceeding 20 pages/2,000 rows remain unresolved. No failed read falls back to an old successful capture. The capture includes a request UUID, transfer/operation correlation and a digest of the exact page query. Accounting re-reads the persisted raw exchange and verifies its response hash, successful HTTP status, capture version, origin/path, request identity and query digest under the existing transfer lock. Monetary JSON tokens are parsed without binary-float conversion.

The approved original provider context must still match the current owned customer/wallet mapping. Every accepted financial row must bind the exact client, customer, wallet, USD authorization currency, provider reference, type and debit direction. The remittance `authCode` must equal the captured transfer system reference. A fee must have its own identity and the documented link to that exact remittance. Missing or ambiguous references, incomplete scans, unsettled records, changed amounts, changed ownership and conflicting captures cannot settle or release funds. The generic normalized Transaction projection, payment status, balance differences, stored zero fees and absence of fee rows are never exact-debit evidence.

## Accounting and integration

The principal reservation and dispatch checks now require the approved source wallet. The final dispatch check also verifies the owned wallet's reserved balance. Existing dynamic customer/beneficiary/amount/purpose handling, server-owned FX audit and expiry, independent checker, durable operation UUID, single-use nonredirecting POST and unknown-outcome no-retry behavior remain in place. Production pricing admission stays blocked.

A completed payout with a matching settled principal debit consumes the original owned principal reservation exactly once. Each separately evidenced settled fee creates an append-only adjustment with provider-event identity and its financial capture reference. Unique event references and transfer/balance locks prevent repeat accounting. Existing owned principal debits are verified and linked through an append-only zero-value reconciliation marker without rewriting or subtracting them again. Unexpected charges record the actual liability even if available funds become negative; this accounting behavior is not authorization to dispatch an unprotected payment. Conflicting charges roll back the accounting savepoint. Principal and charge entries retain the original operation, provider context, reference, source currency and evidence hashes.

Status-only success, rejection, return and webhooks do not prove wallet debit or refund. They preserve unresolved SGD reservations, including hard submission rejections after the dispatch attempt. Duplicate or delayed webhooks cannot debit or release those funds. Known-reference status reconciliation and its existing scheduler revisit terminal SGD operations for delayed financial evidence and later fee rows; a stale lifecycle timestamp does not suppress independently valid financial evidence. A genuinely uncaptured missing-reference outcome still requires authoritative provider resolution and never triggers another Remittance POST.

Refund/reversal/waiver records, including reversals linked to a posted fee, require controlled financial review. This increment does not infer refund amounts or automatically reverse posted entries or release a failed payout's hold. It preserves history and unresolved reservations. A transfer can therefore have terminal payout status while financial reconciliation remains unresolved. The API/UI present observed debit separately from reviewed expected debit, and enable explicit terminal wallet reconciliation without offering another payment submission. Absence of fees does not become confirmed zero or a claim of final charge completeness.

Provider balance refresh records provider snapshots without replacing balances already managed by ledger entries. This prevents a provider debit from being reflected first through snapshot replacement and again through event reconciliation. Reconciling unrelated funding or balance discrepancies still requires an audited financial adjustment, rather than overwriting the ledger from a balance snapshot.
